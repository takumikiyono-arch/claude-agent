# 商談事前準備スキル（この環境向け再設定版）

商談・面談の前に、取引先との過去の経緯・現在の取引状況・先方の課題仮説をファクトベースで整理する。

「次回の面談で何を話すべきか」「先方は何で困っているのか」を、議事メモ／商談メモや Gmail のやり取りから根拠を引いた状態で提示する。

> **このファイルについて**
> claude.ai 版「商談事前準備スキル」を、**このリモート実行環境（Claude Code on the web）で動く形に再設定**したもの。
> オリジナルは Salesforce（`sf` CLI / SOQL）を一次データ源にしていたが、**本環境には SFDC が一切存在しない**（`sf` CLI なし・SF系環境変数なし・Salesforce MCP なし）。
> そのため、SFDC が担っていた役割を **接続済み MCP（Notion / Gmail / Slack / Box / Google Drive / Google Calendar）** で代替する。詳細は次節の対照表を参照。

## このスキルでやること

- **情報収集（並列）**: Notion（企業DB・議事メモ/商談メモ）、Gmail、Slack、Box / Google Drive を横断して取引先関連情報を集める
- **整理**: プロダクト別×フェーズ別の進捗、キーマン、競合動向、Dead 商談の理由を整理
- **課題仮説の抽出**: **先方の業務上の課題**を、商談メモ／議事録／メールから根拠付きで抽出する
- **アウトプット**: `<取引先名>-meeting-prep/meeting-prep-summary.md` を作成、ユーザー確認後に Notion 議事メ모を作成

## このスキルでやらないこと

- pptx 資料の作成（別途依頼があった場合のみ対応）
- 提案ストーリーや営業戦略の組み立て（事前準備は事実整理が主目的。提案検討はユーザーが summary を見て進める）
- 商談データの更新（**読み取り専用**。書き込みは Step 8 の議事メモ作成のみ、かつユーザー確認後）

## 5つの原則（最重要）

事前準備サマリの品質は、以下の5原則で決まる。**毎回ここに立ち戻って自己チェックする**。

### 原則1. 「先方の課題」と「自社の営業課題」を厳密に分離する

「先方の課題」＝お客様の業務上の困りごと、目指す姿、解消したい状態。
「自社の営業課題」＝受注確度、提案戦略、競合優位性、社内体制など。

事前準備サマリでは**先方の課題のみ**を「課題」として扱う。営業課題は別セクション「商談を進める上での社内的な論点」として書く。

**地雷例**：
- ✗「Vista商談が過去2回Deadしている」→これは自社の営業課題
- ○「配車業務がベテラン3名の経験値に依存し、3年以内に全員退職予定」→これは先方の業務課題

### 原則2. ファクトベース原則：推測でデータを補完しない

固有名詞・数値・人物名・システム名は、必ず一次情報（商談メモ／議事録の本文、Gmail、Box/Drive 資料）から取る。「○○と言っていた」「○○記載あり」と引用元を示す。

一次情報から取れない情報は「取得できない」「情報なし」「要確認」と書く。**推測で埋めない**。

**地雷例**：
- ✗ 基幹システム名を勘で「JUST-DB」と書く（実際は AS/400 だった）
- ✗ 競合製品名を一般論で書く
- ○「商談メ모（YYYY/MM/DD）に "基幹は AS/400" と記載」と引用する

> 本環境ではこの原則が特に重要。SFDC で裏取り（再集計）ができないため、**数値・ステータスは「記載ベース」であることを必ず出典に添える**。

### 原則3. 課題と必須要件・前提を区別する

「これができないと前に進めない」レベルは**必須要件・前提**であって課題ではない。

**地雷例**：
- ✗ 基幹システムへの車番データ戻し連携を「課題」に書く
  → 先方が「これは目的じゃない、これができないと請求にもならない」と明言（必須要件）
- ○ 必須要件は別セクション「前提・必須要件」に書く

### 原則4. 提案・強み・解決策を課題スロットに混ぜない

課題セクションは**課題のみ**。解決の方向性は別セクション。

**地雷例**：
- ✗ 課題リストの3番目に「【Hacobuからの提案】段階的な導入アプローチ」と書く
  → これは課題ではなく解決策。混ぜると「読み手が混乱する」とフィードバックされる
- ○ 解決の方向性は「解決の方向性（Vista）」セクションでセットで対応する

### 原則5. 取引先・金額・日付の表記規約（.claude/rules/ が無いため本スキルに転記）

- **取引先**: **「取引先名（部門名）」で識別**（部門名 = Site）。可能なら Notion レコードURLを併記。
  - 本文中の取引先言及でも、`常温福岡センター` のような **部門名単独は避ける**。必ず `ヤマエ久野（常温福岡センター）` のように親会社名を併記する
  - キーマン表・契約更新表・拠点一覧など、サマリ全体で部門名単独表記がないかセルフチェックする
- **金額**: 本環境では `MRR__c` を SFDC から取得できない。Notion／資料に記載のある金額のみ、**単位（万円など）と出典を添えて**転記する。
  - **数字の出典**: SFDC が無いため「SFDC集計」は使えない。Notion の pptx・スライドの数字を載せる場合は「Notion〈ページ名〉記載」と**出典を明記**し、突き合わせ先が無い旨を添える。複数ソースで数字が食い違う場合は両方併記し「要確認」とする（**勝手に一方へ寄せない**）。
- **日付**: `YYYY/MM/DD` または `YYYY-MM`
- **会計年度**: FY9 = 2023年6月〜2024年5月（6月始まり）。他 FY は同様に1年スライドで算出。

## 実行手順（再設定版）

> 各ステップは「**オリジナル（SFDC前提）→ 本環境での代替**」の形で示す。可能な収集は**並列**で進める。

### Step 0: 面談対象の特定（追加）

ユーザーの指示（取引先名）が曖昧な場合や「次の面談の準備」と言われた場合は、**Google Calendar** で直近〜1週間先の予定を確認し、対象の面談（相手・日時・出席者・件名）を特定する。

- `list_events` で当日〜7日先を取得し、商談・面談らしき予定を拾う
- 出席者のメールドメインは Step 4（Gmail）の検索条件に使える

### Step 1: 取引先（企業）を特定する

- **オリジナル**: `sf data query --file query_accounts.soql ... accounts.json`
- **本環境**:
  1. **Notion 企業DB**（`collection://343ee211-8f77-81ef-8b53-000b59235cae`）を取引先名で検索（`notion-fetch` で企業DBを開き、`notion-query-data-sources` で `名前 LIKE '%取引先名%'` など）。
  2. 併せて `notion-search`（query_type: internal）で取引先名を全文検索し、企業DBに無くても関連ページを拾う。
  3. ヒットした企業ページの **URL・正式名称・部門/拠点** を控える（→ 原則5の表記に使用）。

複数該当する場合は、ユーザーに「どの取引先を指していますか？」と確認するか、全件を対象にする方針を提示する。
企業グループ（親子）がある場合は、グループ全体を対象にするかをユーザーに確認する（オリジナルの `common-corporate-group-analysis` 相当の判断を、企業DBのグループ/関連リレーションを辿って手動で行う）。

`accounts.json` 相当の生データは、企業DBの該当行を `accounts.json`（取得できた項目のみ）として保存してよい。

### Step 2: 商談・取引状況の把握

- **オリジナル**: Account 配下の全 Opportunity を SOQL 取得（StageName / MRR__c / IsWon 等）
- **本環境**:
  1. **議事メモ DB**（`collection://ff44bf23-9ca7-4d9d-955e-03c11acf1d98`）を取引先で検索。`企業DB` リレーションが対象企業を指す行、またはタイトル/本文に取引先名を含む行を集める（`notion-query-data-sources` で `名前 LIKE` ＋ `Date` で絞り込み）。
  2. `notion-search` でも取引先名を検索し、商談メモ／提案資料ページ／過去議事メモを拾う。
  3. 拾えた範囲で「**案件 × プロダクト（Vista/Berth/Adapter 等）× ステータス × カウンターパート**」の一覧を組む。
     - **進行中 / 成立 / Dead** の分類は、議事メ모や資料の記載から判断する。
     - `StageName` / `Probability` / `MRR__c` は SFDC 値が無い。**記載があるものだけ出典付きで**載せ、無い項目は空欄＋「SFDC未接続のため不明」とする。
  4. **MRRネット（新規/追加成立 − 解約）** は、記載値が揃う場合のみ算出し「（Notion記載値による暫定値）」と注記。揃わなければ「算出不可（SFDC未接続）」と明記。

### Step 3: 過去商談の本文（文字起こし/メモ）の取得

- **オリジナル**: OpportunityDraft\_\_c の `meetingNote__c`（文字起こし）を `drafts/<id>.txt` に保存
- **本環境**: 文字起こしの一次ソースを以下の優先順で当たる。
  1. **Notion 商談メ모/議事メモ本文**: Step2 で拾ったページを `notion-fetch` で本文取得。長い場合は分割。
  2. **Box / Google Drive**: 取引先名で `search_files`（Drive）/ `search_files_keyword`（Box）し、議事録・録画文字起こし・提案資料を取得（`read_file_content` / `get_file_content`）。
  3. **Gmail**: 上記で取れない場合は Step4 のメール本文を課題仮説の根拠にする。
  - 取得できた本文は `drafts/<source>-<id>.txt` 等として保存（1ファイル1ソース）。**>10000字は Read の offset/limit で分割読み**。

**必須取得対象（情報欠落防止）**:
- 次回面談対象の案件に紐づくメモ/議事録は**可能な限り全件**
- 直近1年以内の **Dead 案件**のメモは**可能な限り全件**
- 進行中案件のうち重要度上位（記載金額や直近性で判断）数件

**Dead 理由の深掘り**（オリジナルの `sales-opportunity-content-analysis` 相当をインライン化）:
Dead の理由がメモ／資料に書かれていない場合、**Gmail（Dead 前後30日のやり取り）と Slack（社内引き継ぎ・懸念）** を一次情報として当たる。確認できなければ「**要確認**」と明記し、**推測で埋めない**。

### Step 4: Gmail の過去やり取り取得

Gmail の `search_threads` で取引先名／相手ドメインの過去90日のやり取りを検索する。

- `"取引先名" after:YYYY/MM/DD`
- ドメインが分かれば `from:@example.com OR to:@example.com`（Step0 のカレンダー出席者から取得）

主要スレッドの本文を `get_thread` で取得し、要点を `gmail_threads.md` にメモする。

### Step 5: Notion 議事メモ・関連ページの検索

`notion-search` で取引先名を検索し、議事メモDB配下のページや関連ページを取得する。
過去の社内議論や議事メモから「未解決の論点」「過去の合意事項」を拾い、`notion_pages.md` に要点をメモする。
（Step1-3 と重複探索になるが、ここでは「社内の論点・経緯」に焦点を当てる）

### Step 6: Slack の社内議論検索（必須）

`slack_search_public_and_private` で **取引先名 + 主要担当者名**を1回は検索する。
「営業同士の引継ぎ」「過去の懸念事項」など、メモに残らない情報を拾うのに有用。

**スキップしない**：ヒット0件でも「Slack 検索済み、ヒットなし」とサマリの「情報の出所」に明記する。時間制約による暗黙のスキップを避ける。

### Step 7: 情報を整理してサマリを作成

`<取引先名>-meeting-prep/meeting-prep-summary.md` を作成する。フォーマットは同ディレクトリの **`output-template.md`** 参照。

**出力は「事前MTGメモ形式」**。狙いは “本番の商談でそのまま話せる事実” を会議で読める粒度で並べること。社内戦略の論評を主役にしない。
参考実例（完成形）: Notion「2026-04-28 ヒューテックノオリン 経営企画役員面談事前MTG」 https://app.notion.com/p/343ee2118f778161a4bfdc84c9d36791

**セクション構成（この順で）**:
1. **概要**: 日時／場所、先方参加者（氏名・役職・補足）、当社参加者、目的、経緯
2. **背景：<取引先>の<状況>**: 経営アジェンダ・物効法/特定事業者該当・物流体制・組織変更など、この面談がなぜ重要かの“地”
3. **<取引先>との提案状況全体像**: 案件×プロダクト×ステータス×カウンターパートの表 → 案件別の詳細（経緯・現状・**先方の業務課題**・根拠リンク）。冒頭に取引規模と **MRRネット**（算出可能な場合のみ。不可なら「算出不可（SFDC未接続）」）を1行
4. **面談の趣旨とアジェンダ案**: 面談の本質的な意味 ＋ アジェンダ案（番号・時間配分付き）
5. **戦略的ポイント**: 自社の営業課題・進め方はここに集約（先方課題とは分ける）
6. **準備事項**: チェックリスト
7. **情報ソース**: Notion(企業DB/議事メモ)/Box・Drive資料/Gmail/Slack（ヒット0件・未接続も明記）。**SFDC は未接続である旨を必ず記載**

**書き終えたら必ずセルフチェック**:
- 課題セクションに「〜が必須」「〜しないと進まない」「〜のためリプレイス必須」など**必須要件と紛らわしい文言**が混入していないか？混入していれば「前提・必須要件」セクションへ移動
- 取引先言及で部門名単独（例: `常温福岡センター`）が残っていないか？親会社名併記（`ヤマエ久野（常温福岡センター）`）に修正
- Hacobu のプロダクト名（Vista/Berth/Adapter等）が **課題セクション** に登場していないか？解決の方向性セクションへ移動
- 数字に**出典**（Notion〈ページ名〉記載 等）が添えてあるか？SFDC で裏取りできない旨が明記されているか？

### Step 8: Notion 議事メモを作成（ユーザー確認後）

ユーザーに `meeting-prep-summary.md` を見せ、内容に問題ないか確認してから Notion 議事メモを作成する。

- 作成先 DB（議事メモ）: `collection://ff44bf23-9ca7-4d9d-955e-03c11acf1d98`
- できれば「商談メ모」テンプレ（`https://app.notion.com/p/131ee2118f7780819fc1ec05f9c8225e`）の構成に合わせる
- ページタイトル: 「YYYY-MM-DD <取引先名> <面談趣旨>」
- 設定できれば `企業DB` リレーションを対象企業に、`タグ` に `02.商談・Onb. Feedback`、`Date` に面談日、`参加者` を設定

## 制約・注意事項（再設定版）

- **読み取り専用**: 既存データを書き換えない。書き込みは Step8 の Notion 議事メモ作成のみ（ユーザー確認後）。
- **SFDC 未接続が前提**: 数値・ステータス・Dead 理由は SFDC で裏取りできない。記載ベースであることを明示し、不明は「要確認」。
- **大きい文字起こしの取り扱い**: 議事録/文字起こしは長文になりうる。`Read` の offset/limit で分割読み。
- **各 MCP が無効/権限不足の環境**: 取得できなかったソースは「〈ソース名〉取得できず（未接続/権限なし）」とサマリの「情報ソース」に明記する。
- **取引先表記**: 必ず「取引先名（部門名）」で識別し、可能なら Notion レコードURLを併記。
